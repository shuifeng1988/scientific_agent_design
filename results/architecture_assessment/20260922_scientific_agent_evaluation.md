# 科研 Agent 合理性评估

评估对象：当前 v0.7.0 源码、科研协议、角色/Skill 定义、provider 交接和执行/验收实现。日期：2026-09-22。采用 scientific-critical-thinking 的“主张与证据匹配、区分结构检查和科学判断”原则；不是临床证据评级。本轮只评估，不修改运行实现或部署，不使用无关项目的后台任务状态评价本框架。

## 总体判断

方向合理，适合定位为**研究者参与决策、具有可替换专业方法的科研项目协作与执行框架**。五根文件、详细计划、任务—结果对应、完整成果包、证据追踪和技术/科学完成分离，是相互支持的设计，应继续保留。

目前证据支持它具有科研流程规范、部分确定性执行能力和模块化接口；不支持宣称它已经是一套跨平台、独立审阅可靠、无需人工介入的全自动科研团队。八个 Skill 和五种角色是能力/职责划分；现有常驻 LLM 适配集中于 Codex planning/repair，其他方法由实际宿主调用。

此前 105 项测试和 9 个 Skill 结构校验通过，证明了测试覆盖的结构、状态和隔离边界。它们没有测量文献深度、统计判断、独立审阅质量或多 Agent 相对单 Agent 的科研收益。本轮没有因代码未变而重复整套测试。

## 合理之处

| 设计 | 为何适合你的目标 | 当前依据 |
|---|---|---|
| 五根文件作为共同指导 | 将科学问题、计划、软件、数据和状态分开组织，又保持统一入口，支持跨会话与跨角色追溯 | project_contract.md、project_template、research_workflow.verify_design |
| 先澄清、调研和方法讨论，再确认正式设计 | 降低从模糊愿望直接跳到工具执行的风险，并保留关键科学选择的真实用户决定 | intake_protocol.md、deep_research_gate.md、research_depth.md |
| 一项计划任务对应一个正式成果包 | 将“做了哪些计算”和“回答了哪个科学问题”联系起来；避免日志和报告失联 | registry/tasks.tsv、validate_tasks、validate_package |
| 方法、表图、结果、结论、解释和 Word 同时交付 | 支持人工阅读和可复核；同源渲染检查能发现部分数值/图像不一致 | research_workflow.py:396–437 |
| 技术 artifact 与科学完成分离 | 已验证中间数据可推进独立计算，最终分析仍须完整报告和解释 | execution_policy.py、supervisor_daemon.py:537–566 |
| 技术恢复与科学修订分开 | 技术失败可以有界修复；科学目的、分母和终点不因报错而漂移 | failure_recovery.md、execution/recovery policy |
| 固定契约、可替换方法 | 能接入新的检索/分析能力，同时维护五根文件和证据标准 | modules.json、module_provider.py、provider_contract.md |
| Agent 与确定性程序职责分开 | 调度、预算、哈希和事件由代码管理；来源理解、设计和解释由研究角色承担 | daemon/driver/event/workflow 实现与角色契约 |

固定五根文件并不要求文件永久不更新：当前 00/01 保护科学基线，02/03/04 可由真实事件维护。严谨规划也不应预先承诺正面结果；原 research_depth.md 已保留零结果、反证和后续分支的意义。

## 主要缺口与优先级

### P0：科学实质审阅尚未与独立审阅记录形成强绑定

`supervisor_daemon.py:129–167` 的 verify_review 核对 QC/reflection 的 run ID、产物哈希、反思字段、文献记录及报告包；`project_events.py:114–124` 在正式完成前再次执行这些检查。但它们没有要求一个独立 Reviewer invocation 的审阅收据、所审版本、具体发现以及缺陷处理状态。

因此“规范要求审阅”与“运行时可验证已完成指定审阅”仍有距离。同一作者可以提供解释/反思记录；当前代码不能由记录结构确定是否存在独立判断。现有规范对此并未承诺所有审阅独立，也不应将其描述为已实现的防错保证。

建议：在正式方案和重要结论的验收节点增加按风险配置的审阅记录，绑定确切输入/输出哈希、审阅调用和发现列表；明确作者回复、必要修订与复查。审阅身份可追溯仍不能自动证明判断正确，需真实任务评价。常规技术 artifact 不必强制增加 LLM 审阅。

### P0：缺少科研行为和产出质量的验收证据

测试主要验证哈希、状态、路径、恢复和报告一致性，不能回答“是否发现最相近研究”“是否识别伪重复”“引用是否支持主张”“是否把相关性说成因果”。图中模块齐全也不构成这些能力的证据。

建议：选小规模、可核验的真实研究任务，同时设置独立的错误注入案例；与重构前入口/单 Agent 方案在相同输入、工具访问和预算下比较。先验证收益，再决定哪些阶段值得独立调用或并行。

### P1：外部模块接口合理，但接入完成度不一致

`module_provider.py` 已实现能力选择、宿主声明、基线/任务绑定和输出交接。`check_output` 对 evidence 进一步验证 appraisal，对 execution/recovery 验证 proposal；其他阶段仍主要检查交接外壳、文件和哈希，后续需外层操作员调用相应验收。

`progress_worker.py:25–59` 已将 execution/recovery 路由接入 Codex 调用。其他能力及 Claude/第三方 provider 由宿主实际调用；不是一套已经在线验收的通用多平台调用器。声明支持某 host/version 也不是能力检测。

建议：先完整接通一个真实外部 evidence provider，包括入口/工具检查、原始输出保存、标准产物转换、限制报告和实质审阅。随后完善各阶段的输入/输出契约和适配器 conformance 测试，不必同时支持所有平台和供应商。

特别需要补齐：通用交接目前没有强制的任务输入 receipts 清单、资源/时间预算字段和各阶段统一的 run/context 绑定。五根文件仍作为共同指导，但具体方法还应绑定它实际读取的数据/模型/代码版本；仅捕捉 00/01 和任务身份不能证明全部方法输入未变。执行契约原有 gates 可以保护部分执行场景，不能自动视为所有 provider 场景已经覆盖。

### P1：科研修订与补充分析的执行闭环不完整

冻结保护是优点；需要补强的是批准后如何有证据地推进新版本。`research_workflow.freeze` 拒绝覆盖已有设计，`research_depth.md:83–91` 明确要求修订草案并说明没有自动应用修订命令，`project_events.py:126–129` 的 amendment 事件记录决定但不替换设计。

另外，`supervisor_daemon.py:554–566` 区分 needs_user 与完成，但 supplement 与 continue 都可走完成路径，并不会仅凭 supplement 自动创建补充任务。不能把“反思提出了下一步”说成“下一步已经被登记并调度”。这不意味着所有 supplement 必须阻止当前任务完成：需要区分影响结论有效性的必需补证据和可选的后续探索。

建议：保留冻结与真实批准要求，增加正式版本修订操作，保存旧基线、任务/结果映射和受影响分支；把必要/可选补充分析落为明确任务，定义分母、多重比较/探索标记、停止标准和依赖。新增修订机制应使用已有规范，不能让研究者不知情地改变设计。

### P1：角色隔离目前主要依赖规则和宿主权限

角色契约要求 Reviewer 不改被审阅产物、worker 不改全局状态；但交接的 protected_paths 是声明，通用检查不是文件系统隔离。Claude Reviewer 适配仍包含 Bash。对于可信工具和人工监督，这可以是初始工作方式；在更高自主性、外部代码或多 Agent 并发时，不能当作强制写权限隔离。

建议：按角色配置只读输入与可写输出目录；只有运行/事件层提交共享状态。先在隔离任务验证，避免把新的权限方案直接施加到活跃研究项目。

### P2：分成更多文件，不自动等于更少上下文或更低成本

现有阶段 Skill 会加载共享规范和相关 references；角色仍遵守读取五根文件的要求。常驻 worker 还加载共同 worker_contract。因此目前模块化收益主要是职责和替换边界更清楚，实际 token、耗时与调用成本尚无测量。

建议：保留五根文件及完整成果要求，测量每阶段实际读取量和重复调用；对相关章节建立可靠定位/索引，避免整套规范反复复制；把重审、重检索和正式报告生成放在合适的任务汇总层。中间 artifact 与正式任务原本已分开，不应给每个下载/分片再强加独立 Word 报告。

## 建议的能力验收任务

| 场景 | 需要观察的行为 |
|---|---|
| 模糊科研方向 | 是否通过真实简短交流形成可检验问题，保持未决项，不制造方法和批准 |
| 有最相近工作与反证的文献任务 | 是否找到并核读关键原始材料、辨别证据支持范围、据此修改或保留方案 |
| 已知配对/聚类结构的数据分析 | 是否保持正确分析单位、估计量与不确定性，并识别刻意设置的伪重复/泄漏 |
| 真实零结果或与预期相反的结果 | 是否保留零结果价值、替代解释和范围边界，而不追逐显著性或改终点 |
| 计算成功但报告失败、远端状态不明 | 是否保留成功证据和作业身份，仅恢复必要阶段，独立分支继续 |
| 更换外部文献 provider | 质量与方法变化是否可追溯；五根文件、任务路径、证据要求和验收是否保持 |

评价指标包括关键主张—原始证据对应准确率、重大设计/分析错误漏检与误报、计划覆盖率、结果可复现性、真实需要用户决定的次数、无进展调用、耗时和费用。先由有领域判断能力的人给出验收标尺，再比较不同配置；不将篇幅、引用数、文件数或 Agent 数作为质量代理。

## 下一阶段顺序

1. 定义少量科学行为验收案例与人工评分标准，同时明确重要节点的 Reviewer 记录。
2. 打通一个外部深度研究 provider 的真实完整交接，检验质量和兼容边界。
3. 补齐计划修订与补充任务落地机制，保持原冻结/任务/结果规范。
4. 基于实际调用数据调整角色隔离、上下文和并发策略。

这些补强沿用现有优点，不需要删除五根文件、放松详细方法与完整成果包要求，也不需要继续无限增加角色数量。本轮未实施这些建议。
